# История изменений

Версия в разработке — 0.1.0. Новые записи добавляются сверху.

## Не выпущено

**Документация и лицензия**

- Добавлена лицензия MIT No Attribution (`LICENSE`): код можно использовать, менять и распространять без ограничений.
- `docs/ARCHITECTURE.md` приведён в соответствие с кодом: фактический состав проектов, схема БД
  (`library.*`, `project.*`), работа с Inventor API в `PdmLite.AddIn.Core` (отдельного `PdmLite.Inventor` нет),
  процесс свойств через Apprentice, `HostKind` вместо несуществующего `IHostCapabilities`; убраны упоминания
  `IFileStore` и `InventorDispatcher`, которых нет в коде; модуль Preview отмечен как не начатый.
- Документы с историей исправлений собраны в этот файл.

**Тесты**

- Тесты разложены по папкам функций (`Backup/`, `Items/`, `Import/`, `Index/`, `Link/`, `Hosting/` …);
  классы, названные по раундам проверки (`ThirdReviewTests`, `SecondReviewTests`, `ReviewRegressionTests`,
  `*AuditTests`), разнесены по классам с именем проверяемой функции. Набор тестов не изменился.

**Код**

- Копирование компонента, поиск и объединение дубликатов вынесены в отдельный `LibraryDuplicateService`,
  восстановление из резервной копии — в `LibraryRestoreService`. Новые сервисы берут базу и папку библиотеки
  у `LibraryItemService` и `LibraryBackupService`, поэтому не могут работать с другой библиотекой.
  `LibraryImportService` и оставшаяся часть `LibraryItemService` разделены на файлы partial-класса по задачам.
- Повреждённый файл настроек больше не теряется молча: рядом сохраняется копия `<имя>.json.damaged-<время>.bak`,
  причина пишется в журнал.
- Ошибки, которые раньше терялись без записи (переименование, обновление связей, неверное сообщение в канале связи),
  пишутся в журнал.

**Сборка и CI**

- Предупреждения компилятора считаются ошибками (`TreatWarningsAsErrors`) во всех проектах, кроме требующих Inventor API.
- `PdmLite.NoInventor.slnf` — решение без проектов с Inventor API; CI собирает его целиком, то есть проверяет
  и модули WPF, а не только тесты.
- Для проектов с Inventor API строгий режим включается вручную: `dotnet build PdmLite.sln -p:PdmLiteStrictInventor=true`.
- GitHub Actions обновлены до версий на Node.js 24 (`checkout@v7`, `setup-dotnet@v5`, `upload-artifact@v7`).

**Установка**

- Новая инструкция [INSTALL.md](INSTALL.md): установка из исходников и EXE, обновление, удаление, где что лежит,
  назначение каждого файла `deploy`, частые проблемы. Краткая памятка — `deploy/README.md`.

### Аудит и рефакторинг основных подсистем

Исходное состояние: коммит `096044e`. Проверены ядро, настройки и загрузка модулей,
индекс и карточки проекта, хранение/импорт/изменение компонентов, резервные копии,
операции с файлами и протокол связи Explorer ⇄ Inventor. Исправления ниже относятся
к подтверждённым дефектам; это не утверждение об отсутствии остальных ошибок.

#### Исправления и разделение ответственности

| Область | Проблема | Итог |
|---|---|---|
| Пути библиотеки | `GetFullPath` принимал абсолютные пути, `..`, альтернативные потоки Windows; обратный слеш не нормализовался на Linux | Общий `ContainedPath` проверяет относительные пути, сегменты, устройства Windows и границу корня. Его используют библиотека, архивы и имена настроек |
| Генерация имён | Расширение могло содержать фрагмент пути; не учитывались COM¹/LPT¹ и CONIN$/CONOUT$ | Проверка расширений и очистка специальных имён до записи |
| Настройки | Разные экземпляры использовали один `.tmp`, мешая параллельному сохранению | Общий `AtomicFile`: уникальный соседний файл, замена после записи, очистка своего временного файла. Сериализация выполняется до записи |
| Конфигурация модулей | `Modules: null`, пустые элементы и повторяющиеся Id приводили к исключениям или неоднозначности | Проверка формата, безопасное включение модулей по умолчанию и диагностическое сообщение |
| Сессия проекта | Проект и дерево менялись до успешного построения индекса; событие могло получить Root другого открытия | Сначала строится полный снимок состояния, затем публикуется одной заменой; событие получает локальное дерево своей операции |
| Обход дерева | Рекурсивный обход мог переполнить стек | Итеративный обход документов и каталогов анализатора |
| Карточки | Десериализация не проверяла null-коллекции, неизвестные уровни замечаний и несогласованные счётчики | Отдельный `ProjectHealthCardStore` отвечает за формат, проверку и атомарное сохранение; анализ не занимается файловым форматом |
| Миграции | Configure во время миграции мог пометить новую БД как уже обновлённую | Снимок конфигурации и сравнение перед фиксацией признака миграции; новая конфигурация мигрируется отдельно |
| Отмена БД | Проверка подключения превращала отмену в обычное сообщение об ошибке | OperationCanceledException передаётся вызывающему коду |
| Удаление компонента | Запись удалялась до файловой операции; заблокированный файл оставлял БД и диск в разных состояниях | Файл временно перемещается до фиксации БД, при ошибке возвращается. Ошибка последующей очистки записывается в журнал |
| Архивы | Циклические разделы вызывали бесконечную рекурсию; повреждённая структура проверялась слишком поздно | Итеративный порядок разделов, проверка родителей и циклов, таблиц, путей и дублирующихся файлов до обращения к БД |
| Контрольные суммы | Добавленный в ZIP файл без записи в Checksums мог не проверяться | Такой архив считается повреждённым, восстановление не начинается |
| Параллельные операции | Создание копий могло использовать общий `.part`; имена временных папок восстановления и журналов зависели только от времени | Уникальные временные файлы/папки и GUID в имени итогового ZIP. Регрессионный тест выявил коллизию при подходе «проверить свободное имя, затем переименовать»; этот подход удалён |
| Каналы связи | Повторный Dispose, параллельное подключение, исключения подписчиков и недопустимые таймауты нарушали жизненный цикл | Идемпотентное завершение, последовательное подключение, отмена подключения при Dispose, изоляция подписчиков, проверка таймаута до отправки запроса |

Схема БД и миграции не менялись. Поддерживаемый формат карточки остался версии 1;
повреждённые карточки требуют повторного анализа. Архивы с недопустимыми путями,
циклами, несовместимым форматом или отсутствующими контрольными суммами отклоняются.

тестовые случаи xUnit, включая строки параметризованных тестов.

Пропусков и ошибок нет. Интеграционные тесты выполнялись с `PDMLITE_TEST_PG`,
а не пропускались. Рост — примерно 22%; измерение покрытия строк не выполнялось.

Новые сценарии включают:

- параллельные записи настроек, ошибку сериализации, отмену и неудачную замену файла;
- пути Windows и Linux, выход из корня, альтернативные потоки, имена устройств;
- повреждённые настройки и карточки, null-поля и неизвестные уровни замечаний;
- деревья и иерархии разделов глубиной 20 000 без рекурсии;
- отменённое/неуспешное открытие проекта без изменения предыдущей сессии;
- обрыв связи, ошибку подписчика, повторное завершение, параллельное подключение,
  неправильные таймауты без запуска обработчика и запрос после отмены;
- смену БД во время настоящей миграции, заблокированной транзакцией PostgreSQL:
  тест ждёт подтверждённого ожидания блокировки через `pg_stat_activity`;
- отказ БД при удалении через тестовый триггер и отказ файловой системы до удаления;
- циклы, отсутствующих родителей, повреждённые таблицы, опасные и повторяющиеся
  пути ZIP, отсутствие контрольной суммы и одновременное создание копий.

Также без ошибок и предупреждений собраны все семь модулей, проект инструмента
миграций и отдельная проверочная сборка реальных окон/модели Explorer без Apprentice.

#### Границы проверки и следующие этапы

Полная сборка AddIn/Explorer и запуск WPF не подтверждены: облачная Linux-среда
не содержит Autodesk.Inventor.Interop.dll и Inventor COM. Windows-ветвь теста
блокировки файла не выполнялась: на Linux проверялся отказ через права каталога.
Нужен прогон в Windows с Inventor 2025, включая подключение, вставку, переименование,
удаление занятого файла, восстановление архива и визуальную проверку карточки.

Проверка `ContainedPath` лексическая: это не разрешение физических junction/symlink.
Работа с библиотекой через такие перенаправления требует отдельной политики.
Атомарность замены одного файла не означает транзакцию между PostgreSQL и диском
при аварийном завершении процесса. Для такой гарантии нужен сохраняемый журнал
восстановления операций и тесты аварийного завершения. Архивирование одновременно
изменяемых в Inventor документов также требует отдельного сценария согласованного
снимка.

Крупные LibraryImportService, LibraryItemService и ProjectFileOperations сохраняют
свою предметную последовательность и существующие регрессионные тесты. Их дальнейшее
разделение на планирование, файловую транзакцию и фиксацию БД стоит выполнять по
отдельным операциям с проверкой в Inventor, а не механически переносить методы.

#### Исправления после проверки пользователем в Windows

Приложение предназначено для Windows; Linux-прогон является дополнительной проверкой,
а не подтверждением готовности в Windows. Пользователь обнаружил реальные ошибки
параллельной замены файла и платформенные ошибки тестовых помощников.

- `AtomicFile` теперь использует общий ограниченный набор `SemaphoreSlim` для
  синхронных и асинхронных сохранений. Путь нормализуется перед выбором блокировки;
  она действует между экземплярами в одном процессе.
- Чтение настроек и карточек открывает файл с `FileShare.Delete`: читатель сохраняет
  прежний снимок, но не блокирует замену файла в Windows.
- Помощники тестов Collector/Relinker и других файловых сценариев возвращают
  нормализованные пути. Очистка Collector снимает ReadOnly независимо от результата
  проверки. Тест ошибки rename принимает IOException или UnauthorizedAccessException
  и продолжает проверять сохранность постороннего файла и очистку временных файлов.
- Добавлены тесты замены при открытом читателе (sync/async) и смешанных sync/async
  сохранений одного нормализованного пути.
- Добавлен GitHub Actions workflow `Windows core tests`, запускающий Core.Tests
  в Release на `windows-latest` при push в main/work и pull request. Результат
  удалённого запуска нужно оценивать отдельно; локальная среда остаётся Linux.

Блокировки записи внутри процесса не заменяют координацию разных процессов или
защиту от сторонней программы, открывшей файл без разрешения удаления.

##### Второй Windows-прогон: уточнённые исправления

Первого исправления FileShare.Delete оказалось недостаточно. Для существующего
назначения теперь применяется File.Replace, а открытые читатели разрешают
FileShare.ReadWrite | FileShare.Delete. File.Move используется только для первого
создания файла. Проверки сохранения старого снимка при открытом читателе сохранены
для sync/async, как и проверки параллельных записей экземплярами настроек.

Дополнительно устранены обнаруженные пользователем расхождения:

- сравнение заголовков каталога утилит учитывает CurrentCulture, а не фиксированный
  порядок латиницы и кириллицы. Тест запускается для en-US и ru-RU; NaturalComparer
  больше не запоминает культуру первого обращения;
- бюджет теста сокращения имени вычисляется от длины папки: длинный пользовательский
  TEMP не превращает сценарий допустимого сокращения в невозможный;
- недопустимое имя папки проверяется до Path.GetFullPath, поскольку нормализация
  Windows может удалить конечную точку и скрыть исходный ввод `a.`.

Workflow Windows tests расширен: оба набора выполняются на windows-2025, где
официально установлен PostgreSQL 17. Для Library.Tests поднимается отдельный кластер
на localhost:55432 с временным случайным паролем; PDMLITE_TEST_PG задаётся для этого
кластера, результаты обоих наборов сохраняются в TRX. Это позволяет проверять
интеграционные сценарии на Windows, а не только Linux. Наличие workflow не является
подтверждением успешного удалённого прогона.

### Регрессионные проверки девяти замечаний ревью

База сравнения — `b77ed99`. Пункт про `Documents.CloseAll(true)` не входит в этот
набор: его семантика требует отдельной проверки в Inventor. Вызов не изменялся.

#### Сначала воспроизведение

До исправлений целевой прогон дал 14 падающих проверок: четыре в Core.Tests и
десять в Library.Tests. Файловое резервирование из InventorAssemblyComponents
сначала было вынесено в DocumentBackupSet без изменения поведения, затем проверено
на реальных файлах. Таким образом, тесты проверяют используемый компонент
резервирования, а не копию его алгоритма в тесте.

Добавлено 16 новых тестовых случаев; дополнен существующий тест ошибки запуска
модулей. Итоговые наборы: Core.Tests — 385, Library.Tests — 563. Все 948 прошли,
без пропусков. PostgreSQL-интеграция выполнялась с PDMLITE_TEST_PG.

#### Совместимость и цена проверок

- Проверка плана теперь блокирует операцию при любом непрочитанном документе проекта,
  включая DWG, который Apprentice не смог распознать. Продолжать с неизвестным составом
  небезопасно. После устранения проблемы чтение повторяется автоматически.
- Состояние индекса с ошибкой сохраняет старые ссылки как справочные; это не разрешение
  использовать их для изменения проекта. API ReadErrorAsync и панель показывают отказ
  явно. Схема БД не менялась.
- Фиксация объединения происходит по одному удаляемому компоненту, как и раньше.
  Успешно выполненные предыдущие компоненты группы не откатываются при следующем сбое.
- Новая проверка архива требует дополнительных проходов хеширования файлов и повторного
  чтения БД, поэтому создание больших копий станет медленнее.
- Проверка согласованности оптимистическая: обнаруженное изменение приводит к отказу,
  а не блокировке стороннего Inventor на всё время копирования. Она не является общей
  транзакцией PostgreSQL/файловой системы и не защищает от аварийного завершения процесса.
- Уже существовавшие до начала копирования внешние изменения файлов сохраняются как
  раньше. Manifest содержит хеш фактически скопированных байтов; БД при этом не правится.

#### Что исполнено и что осталось проверить

Тесты исполнены локально на Linux с настоящей PostgreSQL. Отказ файловой операции
на Linux моделировался правами каталога; в том же тесте для Windows предусмотрена
блокировка файла открытым дескриптором без FileShare.Delete.

Собраны модули связей, библиотеки и переименования, а также проверочная сборка окон
Explorer. Сам AddIn с Inventor API не собран и не запускался: в среде нет
Autodesk.Inventor.Interop.dll и Inventor COM. Для пункта о копиях проверен извлечённый
файловый компонент, включённый в AddIn, а не реальные вызовы замены Inventor.
Реальное поведение Apprentice и визуальное отображение ошибки панели требуют
Windows-прогона. Изменения подготовлены локальным коммитом; push не выполняется.

Следующие исправления неполного отката и шести новых замечаний описаны в

#### Дополнительная очистка

- Подписки Inventor подключаются отдельным Attach после регистрации владельца. Синхронизация активного проекта имеет отмену и отслеживаемые задачи. Поздние COM-события после остановки игнорируются.
- Модуль библиотеки отменяет отложенное резервное копирование и ожидает его в ShutdownAsync. Ошибка одного шага очистки не пропускает остальные шаги или ожидание задачи.
- PdmHost ожидает асинхронную остановку модулей, их областей событий и контейнера; logger освобождается последним. Повторный Start/Dispose не дублирует операции.
- IPdmModule получил ShutdownAsync с реализацией по умолчанию через существующий Shutdown. ConfigureServices предназначен для регистраций: запуск ресурсов нужно откладывать до Initialize/фабрик контейнера, а не выполнять побочные действия при регистрации.

#### Границы проверок

Тесты используют настоящие файлы, очереди, потоки, named pipes и PostgreSQL. На Linux STA-helper выполняется как обычный рабочий поток для проверки очереди; Windows CI дополнительно использует настоящий STA. Полная активация, UI и COM-события требуют приёмки на Windows с Inventor 2025.

Нельзя безопасно принудительно прервать зависший COM-вызов внутри процесса. При таймауте вызывающие задачи уже завершены, но завершающийся STA и его ресурсы остаются до возврата native-вызова. Для жёсткого завершения нужен отдельный процесс; служебный ApprenticeHost уже использует процессную изоляцию.

После исключения CommitAsync отсутствие строки в одном контрольном чтении не доказывает откат неизвестного исхода COMMIT. Поэтому сомнительная копия сохраняется с явным сообщением для проверки, вместо риска удалить файл уже зафиксированного компонента. До начала фиксации отмена очищает незарегистрированную копию штатно.

Журнал настроек обеспечивает восстановление согласованной пары для участвующих читателей/писателей JsonSettings и редактора. Он не является транзакцией PostgreSQL и не переносит уже начатые файловые/БД-операции в другое подключение.

### Совместимость связи, уведомления Content Center и удаление

#### Изменения

- При подключении Explorer к Inventor, передаче аргументов второму Explorer и команде плагина «Показать в Explorer» выполняется общий handshake: проверяются приложение, наличие ответа и точное совпадение версии протокола. Разные версии приложения с одинаковым протоколом разрешены. Неизвестный ping и некорректный ответ считаются ошибкой совместимости. До успешной проверки команды не отправляются.
- Ошибка совместимости передаётся в строку состояния Explorer с подсказкой об обновлении. Повторные одинаковые ошибки не публикуются бесконечно. После обновления плагина штатное переподключение восстанавливается. Второй Explorer при несовместимости не переходит к запуску нового экземпляра: исключение доходит до обработчика ошибки запуска.
- Новые запросы явно объявляют `protocolVersion`. Сервер отклоняет несовместимые запросы до вызова обработчика. Отсутствующее поле означает исходный протокол v1 — это сохраняет совместимость с существующими клиентами текущей версии, но не позволит принять их автоматически за будущую v2. Дополнительное поле не требует менять текущую версию протокола: старые v1-серверы игнорируют неизвестные JSON-поля.
- Обработчик вставки Content Center сохраняет `kEventNotHandled`. Получение COM-данных и публикация необязательного уведомления выполняются через защищённую границу. Недоступные обязательные пути приводят к пропуску уведомления и диагностике; сбой чтения обозначения оставляет его пустым, не мешая предупреждению. Отказ чтения не прерывает событие вставки.
- `deploy/uninstall.ps1` проверяет Inventor и Explorer до удаления. Уже отсутствующие файлы допускаются; отказы доступа и оставшиеся файлы приводят к ошибке с указанием пути и коду завершения 1. Регистрация плагина удаляется после удаления программных папок. Сообщение об успехе выводится только после полного выполнения. Скрипт предназначен для ручной установки `deploy/install.ps1`: EXE-установка направляет пользователя к штатному деинсталлятору Inno, чтобы не оставлять некорректную запись установленного приложения. Библиотека, база и настройки сохраняются.

<a id="import-installer-fixes"></a>

### Проверка импорта и обновления установщика

#### Поведение

1. Импорт сборки подтверждается повторным чтением ссылок после последней записи свойств. Сравнивается полный набор ожидаемых библиотечных путей, проверяется наличие файлов. При несовпадении или ошибке чтения копия удаляется, запись компонента, его версии, связей и журнала не фиксируется. Исходники не изменяются.
2. Очередь импорта строится по графу зависимостей за O(компоненты + ссылки). Вложенные и общие подсборки вносятся раньше родителей независимо от порядка входного списка. Циклы и зависимые от циклов сборки получают явную ошибку до копирования. Независимые компоненты продолжают импортироваться.
3. Новый EXE-установщик не передаёт административный пароль ни через `-Password`, ни через `--superpassword`. Создаётся защищённый Windows named pipe, доступный инициатору и администраторам. Перед отправкой проверяется PID подключившегося процесса. Повышенный PowerShell пишет пароль в приватный файл параметров EDB, задав ACL администраторам и SYSTEM до записи. Срабатывание UAC под другой учётной записью не требует расшифровки DPAPI исходного пользователя. Файл параметров удаляется при успехе и при исключении. Внезапное завершение процесса/ОС может оставить приватный временный файл; доступ к нему остаётся ограниченным ACL.
4. Inno перед установкой резервирует три программные папки целиком. Новая версия устанавливается в пустые папки, поэтому устаревшие модули и зависимости не подхватываются загрузчиком. При ошибке восстанавливаются прежние папки. Журнал пишется атомарно; ошибки восстановления не уничтожают резервные файлы. После успешной настройки сбой очистки не вызывает откат. Настройки, библиотека и PostgreSQL вне этих папок не перемещаются. Данные библиотеки внутри программных папок блокируют обновление. При удалении старых файлов junction/symlink не обходятся.

#### Тесты

- `ImportIntegrityTests`: отсутствие замены, частичная замена, потеря замены при сохранении свойств, ошибка повторного чтения; вложенность из нескольких уровней с общей подсборкой; цикл и зависимая сборка при независимой детали. Тесты работают с файлами и настоящим PostgreSQL, проверяют БД и сохранность исходников.
- `PostgresSecretChannelTests` (Windows): передача правильному PID; отказ другому процессу без раскрытия пароля; завершение клиента до подключения; отмена ожидания.
- `deploy/installer/test-postgresql-options.ps1` (Windows PowerShell): действительные NTFS ACL, отсутствие пароля в аргументах дочернего процесса, удаление файла после успеха/ошибки; отказ неверному hash и неверному формату секрета. Запуск EDB заменён проверяющей заглушкой, сам сервер тестом не устанавливается.
- `deploy/installer/test-update.ps1`: обновление без старых модулей; полный и частичный откат; откат первой установки; защита границ транзакции; защита библиотеки; очистка junction/symlink; реальный отказ во втором переносе через заглушку операции; сохранение копий при заблокированном откате; повторный откат; сохранение новой версии при отказе очистки.
- Windows CI дополнительно компилирует оба рецепта Inno Setup с фиктивной полезной нагрузкой.

Проверки на Linux не подтверждают работу NTFS ACL, UAC, Windows named pipes, реального EDB или Apprentice COM. Для полного приёмочного теста требуются Windows, Inventor 2025 и реальные CAD-файлы: проверить импорт вложенной сборки, затем убрать исходную папку и открыть библиотечную сборку. Проверить установку с UAC от обычного пользователя, установку под другой административной учётной записью и обновление с удалённым модулем.
